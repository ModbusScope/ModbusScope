Adding and editing data points

A review of the Signals dialog (RegisterDialog), its Add popup (AddRegisterWidget) and the Compose expression dialog (ExpressionsDialog). It lists the pain points found in the code and screenshots, what can change in the GUI alone, and what the existing adapter protocol already makes possible.

Summary

Three things hold the workflow back

Syntax is the main interfaceAfter a signal exists, the only way to change its address, type or device is to edit ${40001@2:s16b} by hand. The structured form is only used once, at creation.
No safety netEvery change hits the model immediately. There is no Cancel, no undo, no delete confirmation, and the expression dialog accepts invalid input.
The add form is easy to missThe structured form hides behind a split-button arrow and closes after every add, so setting up 10+ signals is slow and repetitive.

The good news: the adapter protocol already has dataPointSchema, buildExpression, describeDataPoint (which returns parsed fields) and expressionHelp. Most of the larger improvements below reuse these calls and SchemaFormWidget; few need protocol changes.

Pain points

Signals dialog

High

Existing data points can only be edited as raw syntax

The Add popup offers object type, address and data type fields, but once the signal exists the Expression cell is a plain text editor or the … button. Changing holding register 5, s16b to input register 5 requires knowing the prefix and Modicon rules.

The two paths teach different mental models: a form on the way in, a mini-language afterwards.

Medium

The add popup behaves like a menu, not a form

  • It closes after every add, so 10 consecutive registers means 10 open/fill/close cycles.
  • A click outside closes it and throws away what was typed.
  • The name resets to the literal text “Name of signal”, not a placeholder, so it is easily added as the real label.
  • No preview of the resulting expression before adding.
  • If buildExpression returns empty, nothing happens and no reason is shown.
  • Relayout needs a synthetic resize-event workaround because QMenu caches layout.

The table shows syntax, not meaning

The Expression column shows ${40003:s16b}*10. Compose expression dialog

High

Accept works on an invalid expression

handleAccept() stores whatever is in the editor. The user sees a red error label but can still apply a broken expression, which then shows up as a red row in the table.

expressionsdialog.cpp:166
High

No way to insert a data point without typing syntax

The dialog has no picker. To reference a second register the user must read the help panel and type ${...} by hand, even though the same form and buildExpression call already exist in the Add popup.

Medium

The editor hides long expressions

The editor is a multi-line QPlainTextEdit with NoWrap and both scroll bars off. Text past the right edge is invisible. Enter inserts a newline instead of accepting, for what is a one-line expression.

expressionsdialog.ui:76-96
Medium

Feedback is coarse

  • On a syntax error everything from the error position to the end of the line turns red, with a -2 offset heuristic.
  • Validation is regex-level; adapter-level errors (address out of range, unknown type) from describeDataPoint are not shown per reference.
  • Test values default to 0, so 100 / ${40001} opens with an error.
  • Test values only accept decimals; 0x10 is rejected though the expression itself supports hex.
  • The manual says “the expression field turns green when the syntax is valid”; the code only colours register references.
expressionhighlighting.cpp:104-127 · expressionsdialog.cpp:112, 145
Medium

Layout spends space in the wrong places

The default size is 823×854 px. The editor takes a large block for one line, the help panel is collapsed below, and Accept/Cancel sit in a side column instead of a standard button box. Only the three buttons are in the tab order.

Proposed direction

One form for adding and editing

The mockups below keep today's feature set: the same columns, the same address fields, the same adapter calls. What changes is where things live and when they are available. Scaling, offset templates, live values and bulk actions are left for later rounds.

Same form, both waysThe Add popup moves into a side panel that is bound to the selected row. Adding and editing use the same SchemaFormWidget.
Syntax stays availableThe expression column and the Compose expression dialog remain for anything beyond a plain data point. The panel never rewrites the parts of an expression it does not own.
Changes can be undoneThe dialog edits a working copy. OK applies, Cancel discards.

Data flow

Editing a reference through the panel

  1. The Signals table selects a row with ${40002:s16b} and passes it to the side panel.
  2. The panel asks the adapter: describeDataPoint("${40002:s16b}").
  3. The adapter returns fields and a description.
  4. The panel fills its form: setSchema(addressSchema, fields). The preview still shows ${40002:s16b}.
  5. The user changes Address to 5.
  6. The panel asks the adapter: buildExpression(fields, dataType, deviceId).
  7. The adapter returns "${h5:s16b}", in its own notation.
  8. The panel replaces the reference span in the row's expression.

This relies on describeDataPoint returning fields with the same keys as addressSchema, plus deviceId. All four adapters (Modbus, BACnet, IEC 104, Dummy) already do this, so only the spec needs updating; see the implementation plan, phase 0.4.

buildExpression replies with the adapter's own notation (${h1:s16b} for ${40002:s16b}), so the panel only rewrites a reference after the user changes one of its fields.

Suggested order

A path in three steps

  1. Safety and clarity. Block invalid Accept, wrap the editor, placeholder name, empty-result error, hex example values, compact layout, manual fix. Each is small and shippable with a test in tst_expressionsdialog or tst_addregisterwidget.
  2. Panel for adding. Cancel with a working copy, the side panel in add mode, Insert data point in Compose expression, and the Data point column.
  3. Panel for editing. Agree the fields contract with the adapters, then add edit mode and reference replacement.
Later

Kept out of this round

  • Scale and offset fields that generate ${x} * a + b, and quick templates such as bit or high byte.
  • Last read value in the table and as example input.
  • Adding a range of consecutive addresses in one step, and a batch describeDataPoints call.
Open questions

Decisions before step 3

Decided

QuestionDecision
The same data point appears twice, e.g. ${40001} - ${40001}. One entry or two?Show duplicates. Each occurrence is its own entry in the list and is edited on its own.
Data points on different devices, e.g. ${40001} * ${40002@2}. Does the signal have one device or one per data point?A Device selector is required for each data point. The address fields shown depend on the selected device's adapter.

Open

  • Should panel edits apply immediately to the row, or on an explicit Apply button?
  • When a data point moves to a device on another adapter, should matching field values be kept, or should the form reset to that adapter's defaults?
  • When the expression does not parse, the list cannot be built. Is showing only the parser error and Edit expression enough, or should the panel keep the last valid list read-only?
